# ADR-0024: Vulkan 管线缓存

- 状态：Accepted
- 日期：2026-10-23
- 背景与问题：Vulkan 后端每次启动都从 SPIR-V 重新编译全部图形管线（示例游戏 19 个），驱动的编译结果不会跨进程保留。M2.5 要求管线缓存。
- 决策：
  - 启动时（逻辑设备与分配器创建后）从用户数据目录（`SDL_GetPrefPath("AnimalEngine", "Engine")`）读取 `vulkan_pipelines.bin`。文件开头的 `VkPipelineCacheHeaderVersionOne`（头版本、厂商 ID、设备 ID、`pipelineCacheUUID`）必须与当前物理设备一致，否则视为别的 GPU / 驱动的缓存，不交给驱动，从空缓存开始；驱动拒绝初始数据时同样退回空缓存。
  - 所有 `vkCreateGraphicsPipelines` 使用该缓存；累计创建耗时与数量。
  - 退出时（销毁设备前）用 `vkGetPipelineCacheData` 取出数据，`writeFileAtomic` 写回（先写临时文件再重命名，崩溃不会留下半个文件）。日志输出管线数量、创建总耗时与缓存来源。
  - 缓存与 OpenGL 无关；macOS 的 OpenGL 驱动自带着色器缓存。
- 主要理由：管线缓存是 Vulkan 的标准机制，实现简单；自行校验文件头避免把不匹配的数据交给驱动（部分驱动对此处理不佳）。
- 代价与风险：多一个用户数据文件（示例约 140 KB）；多个进程同时退出时后写者覆盖前者（原子重命名保证文件完整）；缓存只随退出写入，崩溃时本次新编译的管线不会保存。
- 验证方式（Release，Apple M2 / MoltenVK）：删除缓存后首次运行创建 19 个管线约 21 ms，之后约 3 ms（进程启动到退出 1.24 s → 约 0.3 s，其中也包含 MoltenVK 自身的缓存效果）；写入随机数据的缓存文件被识别为不匹配并从空缓存开始，下一次运行正常加载；渲染回归两后端与基准截图逐像素一致、验证层零报错。
- 重新评估条件：管线数量大幅增加（需要后台预编译 / 管线库）、或需要随发行包附带预热缓存时。
