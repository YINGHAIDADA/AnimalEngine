# ADR-0027: 参数表（Tuning）：可被数据覆盖、可实时调整的游戏参数

- 状态：Accepted
- 日期：2026-10-23
- 背景与问题：玩家物理（跑速、重力、跳跃、coyote time…）、攀爬、游泳与烟雾动力学参数都写在 C++ 结构体的默认值里，调手感必须改代码再编译；PROJECT.md 要求“参数热调”和“数据与代码分离”。
- 决策：
  - `animal::Tuning`（framework）：代码用 `add("player.runSpeed", &params.runSpeed, min, max)` 登记参数（float / int / bool），登记时的值即“内置值”。名称按 `组.参数` 组织。
  - 数据文件 `world/tuning.json`：`{"format": "animal-tuning", "version": 1, "values": {"player.runSpeed": 90}}`，**只记录与内置值不同的参数**。启动时读取（发行构建同样读取，它是游戏数据）；未知名称与类型错误逐条报告并跳过；不是合法参数文件时什么都不改。`apply(..., dryRun)` 只检查不修改，热重载先用它确认文件有效，再恢复内置值后应用，坏文件不会把参数改乱。
  - 示例游戏登记了 `player.*`（15 项）、`climb.*`、`swim.*`、`smoke.*`。参数面板按组显示滑条，修改过的项高亮并可单独恢复；“Save”写回源文件（ADR-0026）。
- 主要理由：参数仍由代码声明（类型、范围、默认值集中在一处），数据文件只描述差异，提交历史能清楚看到手感调整；同一张表既服务运行时加载，也服务调试面板与热重载。
- 代价与风险：参数通过指针绑定，对象必须比参数表活得久（示例中都是游戏成员）；改名会让旧文件中的名称变成“未知参数”警告，需要同时更新文件。
- 验证方式：单元测试（应用、试运行、类型错误、坏文件、只写差异、往返）；空的 `tuning.json` 下渲染回归不变。
- 重新评估条件：参数很多或需要按房间 / 难度切换时，引入多张表与覆盖顺序。
