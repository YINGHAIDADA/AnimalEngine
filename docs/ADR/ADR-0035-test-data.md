# ADR-0035: 测试使用独立的测试数据

- 状态：Accepted
- 日期：2026-10-24
- 背景与问题：自动测试（无头通关、路线测试、渲染回归、烘焙与 Tiled 往返的单元测试）此前都读取游戏内容（`assets/source`）。修改关卡或预设就会让测试失败，需要重录路线、刷新基准截图——编辑内容与测试互相牵制。测试的职责是验证引擎与玩法的能力和全部渲染效果，而不是验证某一版内容能否通关。
- 决策：
  - **测试数据**：`tests/data/` 是一份完整、只给测试用的数据目录：世界与房间、Tileset、观感 / 效果 / 植物预设、参数表、贴图、音效和烘焙清单。构建时部署到 `bin/<Config>/test_data/`，并复制编译好的着色器。
  - **`--data=目录`**：引擎从指定目录读取数据（不再自动挂载可执行文件旁的 `data.pak`；`--pack` 仍可挂载在该目录上）。此时开发工具关闭（没有可保存的源文件），游戏不读写存档。所有游戏测试都带 `--data`。
  - **测试房间**（`tools/scripts/make_test_data.py` 生成）：
    - `render_*`：最初三个房间的冻结副本，供演示路线（`demo_playthrough`）与渲染回归的光照、烟雾、水、瀑布、植物、藤蔓场景使用；`render_mechanisms` 把全部机关的外观放在一个场景里（平台、门、宝石门、开关、宝珠、发光尖刺、淹没水域与水流、爱心）。
    - `test_*`：每个房间只测一项能力，输入只是按住一个方向键或不按（`tests/input/`）：房间切换、平台携带、平台挤压、坠落平台与向下切换、尖刺扣血、击倒回满、甲虫扣血、开关开门、门保持关闭、其他房间的标志开门、下潜（有能力 / 无能力）、水流携带、宝石门开 / 不开与终点、游上进入上方房间。ctest `capability_*`。
  - **单元测试**：烘焙器、Tiled 往返、预设格式、精灵表导入与音频测试都读取 `tests/data`。
  - 原先针对示例区域的路线测试删除；内容是否好玩、能否通关由试玩判断。CI 的打包任务仍然烘焙并校验游戏内容——那是发行构建的完整性检查（引用缺失或数据无效的内容不能发行），不是玩法测试。
- 主要理由：测试只依赖自己的数据，编辑内容永远不会使测试失败；每项能力一个房间、输入极简，失败时一眼能看出是哪项能力坏了，也不会因为调整跳跃手感之类的改动而大面积失效。
- 结果：修改游戏内容（实验：在入口房间中间砌一道墙挡住演示路线）后，21 个 ctest 与 8 个渲染场景全部照常通过。测试数据约 650 KB（其中环境声 265 KB）。
- 代价与风险：测试数据是内容的一份副本，引擎新增功能时要同时在测试房间里覆盖；测试用的贴图与预设不会随游戏美术更新，渲染回归验证的是渲染器而不是当前美术。
- 验证方式：ctest（`demo_playthrough`、`capability_*`、单元测试）；`render_regression.py` 两个后端 8 个场景；上述修改内容的实验。
- 重新评估条件：测试数据的维护成本明显上升时，考虑由脚本从更小的描述完整生成（包括贴图与音效）。
