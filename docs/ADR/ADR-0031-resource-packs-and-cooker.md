# ADR-0031: 资源包与 Asset Cooker

- 状态：Accepted
- 日期：2026-10-23
- 背景与问题：M5 要求“源资源确定性地生成发行资源”，并能报告缺失 / 重复 / 未引用的资源、对比优化前后的体积与加载性能。此前游戏直接读取构建复制到 `data/` 的源文件：47 个运行时需要的文件加上开发工具与测试用的文件散在三个目录里，JSON 带缩进，每张精灵表与配套贴图各占一个纹理，发行包会依赖开发期的目录结构。
- 决策：
  - **资源包 `data.pak`**（`engine/include/animal/core/pack.h`）：文件头（"APAK"、格式版本、条目数、资源目录偏移 / 大小、目录哈希）+ 数据版本字符串 + 各条目数据 + 资源目录（路径、偏移、存储大小、原始大小、压缩方式、内容哈希）。每个条目单独用 zstd 压缩（压不小的条目原样存储）；内容相同的条目只存一份；条目按路径排序、不记录时间戳，同样的输入得到逐字节相同的包。读取时校验目录哈希与每个条目的内容哈希，格式版本不同直接拒绝并说明。写包放在单独的目标文件中，只有烘焙工具和测试链接压缩器。
  - **挂载**（`core/file`）：`mountPack(包, 目录)` 之后，该目录下的所有路径（`readFile` / `fileExists`）**只**从包中读取；包里没有的文件即使磁盘上存在也读不到，发行版不会意外依赖散文件。目录之外（存档、设置、管线缓存）照常读写磁盘。游戏启动时挂载 `--pack=路径` 或可执行文件旁的 `data.pak`，否则读散文件；上层加载代码没有任何改动。开发工具发现数据来自资源包时自动关闭（没有可编辑、可重载的源文件）。
  - **Asset Cooker**（`tools/asset_cooker`，`AnimalCooker`，链接 framework）：从 `assets/cook.json` 清单出发——世界文件、代码直接引用的预设（蜡烛、溅水、宝石火花效果、草的种类、参数表）、精灵表、材质、渲染器需要的着色器——沿引用收集：世界 → 房间 → Tileset、Tiled 中所有 `file` 类型属性（观感、效果、植物）→ 观感的 `base` 链。每个文件用游戏自己的解析器在烘焙前、烘焙后各校验一次；引用不存在或数据无效时烘焙失败。
  - **格式转换**：JSON 去掉空白与 Tiled 的编辑器字段（`tiledversion`、`editorsettings`），运行时仍是同一条 JSON 解析路径；着色器包原样放入（已是二进制）。
  - **图集**：清单中的材质（同一目录）合成一张图集：架子式装箱（按高度、宽度、名称排序，宽度取能放下最宽图像的最小 2 的幂），albedo / 法线 / 自发光三页使用同一布局，缺失的配套贴图与空白处填渲染器的默认值（平面法线、不发光）。页面存为原始 RGBA8（"ATEX"：版本、宽、高、直通 Alpha 像素），交给包压缩，运行时不再解码 PNG。`textures/atlas.json` 记录每个材质的区域；`loadMaterial` 发现目录里有图集索引且列出了该材质时，返回共享图集纹理上的区域（引用计数，最后一个材质释放时销毁）。`LoadedTexture` 增加区域偏移，渲染器换算 UV（尺寸取 `Device::textureExtent`），游戏代码不变。
  - **报告**：每次烘焙输出文本摘要与 `cook_report.json`：各类（着色器、纹理、关卡与预设）的文件数、源大小、烘焙后大小、存储大小；内容重复的源文件；未被引用（因此不打包）的文件；错误。`AnimalCooker --verify` 挂载一个包，按游戏的方式加载世界、所有房间与观感、精灵表、着色器与图集页，确认完整可用（不需要 GPU）。
  - **发行布局**：CMake 目标 `animal_package` 烘焙并校验 `data.pak`，与可执行文件放到 `build/<preset>/package/<Config>/`。CI 在 macOS 与 Windows 上各打包一次（关闭开发工具），同一台机器烘焙两次逐字节比较，两个平台的 `data.pak` 哈希也必须相同，结果作为构建产物保存。
- 主要理由：在文件层挂载让资源包对引擎、框架和游戏透明，开发期的热重载与发行期的资源包共用全部加载代码；用游戏自己的解析器校验，保证“烘焙通过”就等于“游戏能加载”；紧凑 JSON 保留单一解析路径，关卡数据小到二进制格式不值得维护第二套加载器。
- 结果（Apple M2，Release）：源数据 166 KB → 包 48.8 KB（着色器 112 → 37 KB，关卡与预设 46 → 6 KB，纹理 8 → 2.5 KB）；12 张纹理合成 128×16 图集（三页），绘制调用平均 13.1 → 10.2；启动时的数据加载（含渲染器初始化）OpenGL 约 21 → 20 ms、Vulkan 约 16 → 13 ms；7 个回归场景从资源包运行与基准逐像素一致。
- 代价与风险：图集要求材质在同一目录且不大于装箱宽度（当前很小，未来可能需要多页）；包内文件是只读的，开发工具在资源包模式下不可用；新增运行时数据必须让引用链或清单覆盖到，否则烘焙会把它列为未引用而不打包（`--verify` 与“从资源包跑回归”会发现遗漏）；每个条目单独压缩，小文件的压缩率不如整体压缩。
- 验证方式：单元测试（包的往返、去重、确定性、损坏与版本检测、挂载规则；真实资源两次烘焙逐字节相同且 `--verify` 通过；缺失引用、无效数据、未引用文件被报告）；`render_regression.py --pack` 7 个场景两后端与基准一致；独立的发行布局运行画面与散文件一致；CI 跨平台哈希比较。
- 重新评估条件：资源量增长到需要流式加载、多个包（基础包 + 补丁）、纹理压缩格式或二进制关卡时扩展格式（文件头已带版本号）。
