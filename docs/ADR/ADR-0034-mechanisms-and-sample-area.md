# ADR-0034: 机关、下潜与示例区域

- 状态：Accepted（路线测试部分已被 ADR-0035 取代：测试改用独立的测试数据）
- 日期：2026-10-23
- 背景与问题：M6 要求“从启动到通关一段完整区域无需开发者手动修补”。此前世界只有三个房间，没有能锁住或打开路线的东西，也没有终点。需要：一组可在关卡编辑器里摆放的机关（移动 / 坠落平台、尖刺、开关与门、水流），一个改变可达范围的能力（下潜），约 10 个房间的示例区域，以及能证明整段区域走得通、并在改动后继续守住这一点的自动测试。
- 决策：
  - **动态实心物**：`TileMap` 增加动态实心矩形，对所有物体（玩家、甲虫、粒子）与实心 Tile 一样生效；控制器、碰撞与巡逻代码因此无需改动。`PlatformSystem`（`framework/platforms.h`）管理往返移动的平台、被站上后抖动再坠落并在一段时间后复位的平台、以及门（不移动、打开即不再实心）。平台逐像素移动：站在上面的玩家随之移动，被平台挤到时推开，推不动即“压扁”（回检查点）。
  - **危险 Tile**：Tile 属性 `hazard` = `up` / `down` / `full`，只在尖端一侧的半格内造成伤害（两侧各留 1 px）；踩到即回到检查点。
  - **水流与下潜**：水域属性 `currentX` / `currentY`（px/s）按淹没比例带动物体（`applyCurrent`）。下潜（`stepDive`）：有能力时在水中按下进入，双轴自由游动（速度归一化、加速度限制），无输入时缓慢上浮；升到接近水面且不按下时恢复漂浮。没有能力时浮力把角色托在水面，水下通道因此成为天然的门槛。参数在参数表中（`dive.*`）。
  - **游戏对象**（`game/src/mechanisms.*`）：`platform`、`door`（`flag` 对应开关，或 `gems` 数量的宝石门）、`switch`、`ability`（`name` = `dive`）、`goal`，以及给测试与传送用的落点 `entry`。开关与能力是存档标志（`switch:名称`、`ability:名称`），所以一个房间的开关可以打开另一个房间的门；门一旦打开就不再关闭（不会压到玩家，也不需要存档门的状态）。终点设置 `finished` 标志并显示通关画面。全部对象都在关卡编辑器的模板中。
  - **示例区域**：`tools/scripts/make_area.py` 生成 7 个新房间（与原有 3 个共 10 个），之后在编辑器中修改；脚本拒绝覆盖已存在的房间。结构：长廊 → 断桥（移动 / 坠落平台、藤蔓）→ 掉入尖刺竖井 → 底部的下潜宝珠与断桥门的开关 → 经烟雾深坑回到长廊（第一圈）；下潜后从烟雾深坑的水池进入淹没区域：地下湖（向东的水流）、沉没神殿（逆流而上，开关打开暗流里的宝石小门）、暗流（向西的水流，向上连回尖刺竖井的水池）、淹没隧道（向上进入闸门大厅的水池）；闸门大厅的宝石门要求 19 颗中的 14 颗，门后是终点。原有房间只改了出口与水池（对象 id 不变）。
  - **路线测试**：`tests/routes/*.txt` 是从某个房间出发的逐帧输入，ctest `route_*` 以无头、确定性、严格模式回放，并用 `--expect` 检查结束时的房间、标志、宝石、是否通关、重生次数。覆盖区域内的每一个连接，以及三个门槛确实挡路（没有下潜、13 颗宝石、断桥门未开）。测试辅助：`--flags=`、`--gems=N`、`--trace[=N]`、`--expect=flag:名称`；`--record-input=路径` 把实际游玩录成输入脚本，修改房间后重录即可。
- 主要理由：把机关做成 Tile 层的动态实心物与存档标志，复用了全部已有的碰撞与存档代码；门只开不关、开关是全局标志，换来零额外状态；用水作为门槛，使下潜既是能力也是关卡结构；路线测试记录的是“结果”，而不是逐帧位置，所以对无关的视觉改动不敏感，且在 macOS / Windows、Debug / Release 上结果一致。
- 结果：10 个房间压缩后约 12 KB；9 条路线测试每条 1–2 秒（Debug）、约 0.2 秒（Release），两个平台、六种构建配置全部通过；录制路线时发现了 5 处走不通或过于苛刻的地方（尖刺上的石块离落脚点太远、石块头顶空间不足、宝珠需要起跳才能拿到、断桥第三级台阶到顶层的间隙过大、坠落平台被台阶压住），均已修正。
- 代价与风险：路线测试是逐帧录制的，修改相关房间后需要重录；宝石的可达性只有部分由测试覆盖；向上的房间过渡需要关卡配合（落脚点或连通的水）。见 [KNOWN_ISSUES.md](../KNOWN_ISSUES.md)。
- 验证方式：单元测试（危险 Tile 的伤害区域、动态实心物、平台携带 / 推开 / 压扁、坠落与复位、门、下潜的归一化与上浮、水流按深度带动）；ctest `route_*`；渲染回归（原有房间改动后只有改动的 Tile 与周围烟雾不同，基准已更新）。
- 重新评估条件：需要会关闭的门、计时开关或多个能力时，门的状态需要进入存档；房间数量增长到手工布局困难时，考虑在世界编辑器中自动检查出口是否对齐。
