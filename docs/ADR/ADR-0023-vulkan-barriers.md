# ADR-0023: 按用途推导的 Vulkan 屏障

- 状态：Accepted
- 日期：2026-10-23
- 背景与问题：验证版 Vulkan 后端的所有图像屏障与上传屏障都是“所有阶段 / 所有内存写 → 所有阶段 / 所有读写”，正确但最保守；另外布局不变时不发屏障，所以同一纹理在相邻两个渲染通道中都作为颜色附件（例如水 pass 写画布、紧接着发光 pass 以 Load 方式继续画）时两次写之间没有依赖，按规范是写后写隐患（同步验证未报出）。M2.5 要求细化屏障。
- 决策：
  - 每个纹理记录上一次的**用途**（`ImageUse`：无、颜色附件、采样、拷贝目标、拷贝源、呈现），每种用途对应确定的阶段、访问与布局：

| 用途 | 阶段 | 访问（写） | 布局 |
|---|---|---|---|
| 颜色附件 | COLOR_ATTACHMENT_OUTPUT | 附件读写（写） | COLOR_ATTACHMENT_OPTIMAL |
| 采样 | VERTEX_SHADER、FRAGMENT_SHADER（GPU 粒子在顶点着色器读状态） | 采样读 | SHADER_READ_ONLY_OPTIMAL |
| 拷贝目标 | TRANSFER | 传输写（写） | TRANSFER_DST_OPTIMAL |
| 拷贝源 | TRANSFER | 传输读 | TRANSFER_SRC_OPTIMAL |
| 呈现 | — | — | PRESENT_SRC_KHR |

  - 屏障 = 上一次用途的阶段与**写访问** → 下一次用途的阶段与全部访问；连续两次只读采样不发屏障，其余情况（包括相同布局的连续写）都发；不需要旧内容时（Clear / DontCare / 整幅上传）旧布局用 UNDEFINED。
  - 交换链图像不跟踪：获取后的布局转换以等待信号量的 TRANSFER 阶段为源，blit 后转为呈现布局。
  - 缓冲上传命令缓冲（排在帧命令之前提交）的首尾各一个内存屏障：拷贝前等待此前对顶点 / 索引 / uniform / 采样数据的读取（读后写），拷贝后让传输写对顶点输入与着色器读可见。
  - 读回后纹理留在“拷贝源”用途，下一次使用时由跟踪自动转回，不再手动恢复布局。
- 主要理由：用途是 RHI 层面已知的信息（渲染通道附件、绑定组采样、上传、呈现），从用途推导屏障既精确又不需要上层声明；补上了相同布局连续写的依赖。
- 代价与风险：在 macOS / MoltenVK 上 GPU 耗时没有可测变化（入口约 1.74–1.82 ms 对 1.77–1.89 ms，烟雾深坑约 2.06–2.08 ms 对 2.00–2.01 ms，均在测量噪声内）——苹果 TBDR GPU 上 MoltenVK 本身就粗粒度地实现屏障，收益预计在 Windows / Linux 的桌面 GPU 上体现，需 Windows 验证时实测；跟踪状态按录制顺序更新，要求命令按录制顺序提交（当前设计如此）。
- 验证方式：渲染回归 6 个场景两后端与基准截图逐像素一致，Vulkan 验证层含同步验证零报错；`--resize-test` 交换链重建 4 次零报错。
- 重新评估条件：引入计算、存储图像、多队列或子资源（mip / 数组层）时扩展用途表。
