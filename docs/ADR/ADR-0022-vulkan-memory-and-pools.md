# ADR-0022: Vulkan 显存子分配、描述符池与暂存缓冲

- 状态：Accepted
- 日期：2026-10-23
- 背景与问题：验证版 Vulkan 后端为每个缓冲和图像单独调用 `vkAllocateMemory`（驱动对分配次数有上限，常见为 4096，且每次分配开销大）；描述符池固定 4096 个 set，用完后创建绑定组直接失败；每帧暂存缓冲固定 8 MB，溢出时每次上传单独建一个缓冲。M2.5 要求“内存子分配”。
- 决策：
  - **VMA**（Vulkan Memory Allocator v3.4.0，子模块，单头文件，MIT）：缓冲与图像通过 `vmaCreateBuffer` / `vmaCreateImage` 分配，设备本地优先（`VMA_MEMORY_USAGE_AUTO_PREFER_DEVICE`）；暂存与读回缓冲要求主机可见且一致（`HOST_VISIBLE | HOST_COHERENT`），创建时常驻映射，不需要手动刷新。VMA 的函数指针取自 volk（`VMA_DYNAMIC_VULKAN_FUNCTIONS`），实现位于单独的 `vk_memory.cpp` 并关闭第三方警告。退出时日志输出分配数、块数与总量。
  - **描述符池**：池列表，每个池 128 个 set（uniform buffer 256、combined image sampler 512）；分配返回 `OUT_OF_POOL_MEMORY` / `FRAGMENTED_POOL` 时新建一个池重试；绑定组记录所属的池，释放时归还到该池。
  - **暂存缓冲**：每帧初始 1 MiB（示例游戏实际每帧不到 512 KiB）；记录每帧需要的最大字节数，溢出的上传仍临时单独分配，该帧槽位下次开始（fence 已完成）时把暂存缓冲扩到需要量的下一个 2 的幂。
- 主要理由：VMA 是业界标准，正确处理对齐、内存类型选择、独占分配与碎片，自写分配器难以达到同等质量；池列表与按需扩容的暂存缓冲去掉了两个硬性上限，且不增加稳态开销。
- 代价与风险：多一个依赖（头文件约 2 万行，编译一次）；MoltenVK 对较大的渲染目标偏好独占分配，块数少于分配数但不是一块（示例：97 个分配、43 个块、82.7 MiB）；描述符池不会收缩。
- 验证方式：渲染回归 6 个场景两后端与基准截图逐像素一致，验证层（含同步验证）与 RHI 校验零报错；临时把每池 set 数改为 8，运行中新建了 9 个池且结果与基准一致；临时把暂存缓冲改为 64 KiB，两个帧槽位各扩容一次到 512 KiB 后稳定，结果与基准一致。
- 重新评估条件：需要显存预算 / 驻留管理、碎片整理、或大量流式资源（M5 资源包之后）时。
